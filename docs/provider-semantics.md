# Provider decisions

Reviewed official API documentation on 2026-10-15. Real-account acceptance remains required.

- [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server): confidential web applications exchange codes with a client secret. This is the unavoidable exception for this server design; there is no documented certificate/private-key client authentication equivalent for this delegated flow. Service accounts/domain-wide delegation would change the user-consent model and privileges. The secret is read from a mounted file, never sent to the browser. PKCE supplements client authentication.
- [Microsoft authorization code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow) and [certificate credentials](https://learn.microsoft.com/en-us/entra/identity-platform/certificate-credentials): use a certificate-backed PS256 client assertion with SHA-256 certificate thumbprint, PKCE and delegated Contacts.ReadWrite. No Microsoft client secret. Deployment pins an Entra tenant issuer; Google and Microsoft logins remain distinct stable issuer/subject identities, never silently joined by email.
- [Google incremental sync](https://developers.google.com/people/api/rest/v1/people.connections/list): keep masks and source selection fixed across pages, commit the final sync token only after the full page set is durable, and treat expiry as reconciliation. Tokens expire after seven days. Change feeds can lag writes; direct reads verify existing mapped contacts before decisions.
- [Google updates](https://developers.google.com/people/api/rest/v1/people/updateContact): retain contact-source metadata and etags, patch only changed fields, serialize mutations. Unsupported fields outside the mask stay untouched. Google deleteContact does not document an atomic etag precondition: a read/delete race cannot be eliminated. Keep deletion disabled until this limitation is accepted during real-account acceptance.
- [Graph contact delta](https://learn.microsoft.com/en-us/graph/api/contact-delta?view=graph-rest-1.0): explicit folder ID, opaque next/delta links constrained to the original host and folder. Hydrate changed contacts to avoid interpreting omitted delta properties as clears. A full reconciliation never turns absence into deletion.
- [Graph contact updates](https://learn.microsoft.com/en-us/graph/api/contact-update?view=graph-rest-1.0): send only changed properties. Structured addresses include their complete common property set. Conditional If-Match is sent; enforcement for the tenant/provider must be verified before enabling live mutation/deletion.
- [Graph extended properties](https://learn.microsoft.com/en-us/graph/api/singlevaluelegacyextendedproperty-post-singlevalueextendedproperties?view=graph-rest-1.0): creates carry a per-operation marker; Google uses userDefined. Neither contact-create endpoint documents a general idempotency key. After an uncertain write, stop automatic creates and recover by the marker. Absence in an eventually consistent read does not authorize a second create.

## Mapping policy

Names (given/family/display), email addresses, typed phones, primary organization (company/department/title), typed structured addresses, plain notes and website values form the common model. Lists use stable ordering. Missing common fields mean unknown; explicit empty values mean clear.

Google email types and provider-only subproperties are preserved on existing values, but Graph has no email type field. Graph email display names are likewise retained on existing values. Custom Google phone types, multiple mobile phones, duplicate address types and multiple websites cannot be represented by Graph: stop the operation for review, retaining source data and snapshots. Do not silently truncate. Multiple Google organizations or names prevent replacing those compound fields. Extra organizations remain at the source. HTML Google biographies are not rewritten as plain text.

Photos, birthdays, groups/categories and other unsupported fields are never included in update masks or Graph patches. Source-specific values are retained in the local snapshots and provider record. This is intentionally not a round-trip export of all provider metadata.

## Safety limits

A Graph contact leaving the selected folder can look like a removal. ID moves and missing mapped IDs need explicit re-linking/reconciliation; do not assume an absent record was deleted. Transient read failures use bounded backoff with Retry-After. Writes are journaled and not blindly retried after network/5xx failures. Access-token refresh is serialized per account; a rejected refresh requires reconnection. Raw provider errors, URLs, contact contents and tokens must never enter logs.
